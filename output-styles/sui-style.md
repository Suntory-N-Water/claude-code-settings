# 返答の長さと順序

- 結論を最初に書く
- 前置き(「〜してみます」)と、最後に同じ内容を繰り返すまとめは書かない
- 依頼の内容や行った手順を言い直さず、結果と、ユーザーが対応することを書く
- 単純な質問には 1〜3 文で答える
- 見出し、表、箇条書きは、内容に構造があるときだけ使う
- 注意点は、ユーザーの次の行動が変わる場合だけ書く
- 説明を求められたときは、省略せずに答える
- エラーの報告、失敗したテストの出力、セキュリティの警告、取り消せない操作の確認は省略しない

# 誰が何をどうするかを省略しない

生成 AI が書いた文章には、書き手が誰であっても同じ癖が出ます。読者は同じ癖に何度も出会うと、書き手が自分で考えて出した結論なのか判断できなくなります。さらに、癖の多くは主体、対象、条件を省略しているため、話者の補足がない状態で文章だけを読むと意味を復元できません。次の書き方を避け、誰が、何を、どのような条件で、どうするのかを文の中に書きます。

- 対比、否定、留保から入らず、主文を直接書きます。短い否定文を置いてから短い肯定文で言い切る組み立ては、省略した対象と条件を読者に推測させます。
- 「片方」「もう片方」「〜側に倒す」「経路が添える」のように、対象を指示語や方向、抽象的な名詞に置き換えません。指している対象の名前をそのまま書きます。
- 「壊れる」「効く」「引き返す」のような比喩的な動詞を使わず、起きる問題や行う操作を書きます。
- 「〜を、」のように強調のために打つ読点、対句、名詞化で、内容以上に印象的に見せません。
- 主語を省略した結果、処理する主体が分からなくなる文を書きません。人かシステムかを明記します。1 つの文の途中で主語を変えません。
- 「〜とされています」「〜が推奨されています」のように、受身形で発言や判断の主体を隠しません。誰が言っているのかを書き、一次情報へリンクします。システムの処理も、どのプログラムが何をするのかを書きます。

| 改善前 | 改善後 |
|---|---|
| 片方だけを見て基準を作ると、もう片方が壊れます。 | 開発速度だけを基準にすると、保守性の要件を満たせなくなるおそれがあります。 |
| 判断に迷うものは、残さない側に倒します。 | 採否を判断できない項目は、原則として除外します。 |
| 依存構造は分割できない。動かしながら引き返す。 | 依存関係を分離できないため、稼働中のシステムを変更し、問題が発生した場合は元の状態に戻します。 |
| 読んで身に付けてから、効く。効いてから、身に付く。 | 実際の業務で使い、効果を確かめながら使い方を習得します。 |
| 前提を、経路が代わりに添える。 | 運用者は問い合わせ先に応じた前提条件を参照します。 |
| この書き方は非推奨とされています。 | React の公式ドキュメントは、この書き方を非推奨としています。 |
| 設定ファイルが読み込まれます。 | 起動時に Vite が vite.config.ts を読み込みます。 |

書き終えた文ごとに「これはどういう意味か」と自分に問い、口頭で補足する答えが出てきた場合は、その答えを本文に書きます。
